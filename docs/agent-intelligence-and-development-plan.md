# 智能 AI 硬件 OPC Agent 智能与开发规划

日期: 2026-06-07

## 1. 一句话定位

构建一个“智能 AI 硬件 + 多角色 Agent 公司操作系统”: 创始人通过一个桌面或随身 AI 硬件入口采集语音、会议、现场观察和任务指令, 再由云端与本地 Agents 自动完成产品、研发、供应链、合规、销售、运营和财务工作, 让一人公司具备小团队级执行力。

## 2. 参考产品边界

当前规划采用可替换参考形态, 不是最终工业设计定案。

推荐 MVP 形态:

- 一个桌面或随身 AI 工作助理硬件, 具备麦克风阵列、低功耗摄像头或视觉传感器、状态灯或小屏幕、物理静音键和本地唤醒能力。
- 一个云端 Agent 控制台, 负责任务分派、文档生成、代码开发、供应链跟踪、客户反馈和经营指标。
- 一个创始人审批台, 把高风险动作集中到人工确认: 花钱、签约、公开发布、隐私策略、合规结论和安全例外。

暂不进入第一阶段的事项:

- 自研大模型训练。
- 直接承诺医疗、金融、安防执法等高监管用途。
- 未经验证的量产成本、认证费用和供应商交期。
- 完全无人审批的资金支付、合同签署和对外承诺。

## 3. OPC 总体架构

```text
Founder
  |
  v
AI Hardware Interface
  - voice capture
  - camera or sensor input
  - local wake word
  - privacy switch
  - status display
  |
  v
Agent Orchestrator
  - task router
  - role registry
  - memory and context manager
  - approval gate
  - audit log
  |
  v
Role Agents
  - strategy
  - product
  - hardware
  - firmware
  - AI and data
  - app and backend
  - QA
  - supply chain
  - compliance
  - finance
  - marketing
  - sales
  - customer success
  |
  v
Systems of Record
  - GitHub repository
  - docs and decision logs
  - issue tracker
  - CRM
  - finance sheet
  - supplier database
  - test evidence
```

GitHub 是技术和产品文档的主事实源。CRM、财务、供应链和测试证据可以外接系统, 但关键结论必须回写仓库中的决策记录。

## 4. Agent 智能等级

为避免把 Agent 设成泛泛的聊天助手, 每个 Agent 都按智能等级分层:

| 等级 | 能力 | 人类审批 |
|---|---|---|
| L0 记录 | 读取、整理、摘要和检索已有资料 | 不需要, 但要可追溯 |
| L1 草案 | 生成 PRD、测试计划、邮件、报价对比、会议纪要 | 发布前审批 |
| L2 工具执行 | 创建 issue、修改文档、运行测试、生成 BOM 初稿、更新看板 | 中风险动作审批 |
| L3 闭环执行 | 根据指标发现问题、提出计划、执行低风险修复、提交证据 | 预算、合规、对外动作审批 |
| L4 经营代理 | 跨角色拆解目标、调度子任务、追踪 KPI 和复盘 | 创始人保留最终否决权 |

MVP 阶段建议最高开放到 L2。进入 DVT 之后, 对低风险内部流程开放 L3。L4 只用于内部建议和编排, 不允许绕过创始人对外行动。

## 5. 多角色 Agents 设计

| Agent | 核心职责 | 智能能力 | 输入 | 输出 | 工具权限 | 核心指标 |
|---|---|---|---|---|---|---|
| CEO Strategy Agent | 公司方向、目标、资源取舍 | 市场假设拆解、OKR 制定、风险复盘 | 创始人目标、市场资料、财务约束 | 季度 OKR、战略备忘录、优先级 | 读写战略文档和路线图 | 每周优先级收敛, 关键假设有验证计划 |
| Product Manager Agent | 产品定义和用户价值 | 用户故事、PRD、竞品对比、需求排序 | 访谈记录、使用场景、商业目标 | PRD、用户流程、验收标准 | 创建 issue、维护 PRD | 每个功能有用户问题和验收证据 |
| Hardware Architect Agent | 硬件系统方案 | 器件选型、功耗预算、接口定义、风险识别 | 产品需求、传感器需求、尺寸约束 | 系统框图、BOM 初稿、接口表 | 读写硬件文档, 不直接下单 | BOM 风险可解释, 关键器件有替代项 |
| Firmware Agent | 设备固件和边缘逻辑 | 驱动规划、状态机、OTA、日志和低功耗策略 | 硬件接口表、传感器协议 | 固件架构、测试用例、开发任务 | 修改固件代码和测试, 运行本地构建 | 关键路径可测, 日志可诊断 |
| AI ML Agent | AI 能力和模型策略 | 任务分类、模型路由、RAG、提示词、评估 | 用户任务、数据样本、成本限制 | 模型选择记录、评估集、提示词版本 | 读写 AI 文档和实验脚本 | 质量、延迟、成本均有量化 |
| Backend Agent | 云端服务和任务编排 | API 设计、队列、权限、审计、Agent 调度 | PRD、Agent 协议、数据模型 | API 规格、服务任务、审计方案 | 修改后端代码和测试 | 关键接口有测试和权限边界 |
| App UX Agent | 创始人控制台和设备交互 | 信息架构、审批流、状态反馈、错误提示 | 用户流程、设备状态、任务队列 | 页面结构、交互文案、可用性检查 | 修改前端文档或代码 | 审批动作清晰, 状态不含糊 |
| QA Reliability Agent | 质量和可靠性 | 测试矩阵、缺陷归因、回归策略、验收证据 | 需求、代码变更、设备日志 | 测试计划、缺陷报告、发布门禁 | 运行测试, 创建缺陷 issue | 发布前关键风险有证据 |
| Supply Chain Agent | 供应商和 BOM | 器件生命周期、报价对比、MOQ、交期风险 | BOM、供应商资料、需求数量 | 供应商短名单、采购建议、替代料 | 维护供应链表, 不付款 | 关键料至少 2 个可行来源 |
| Compliance Agent | 法规、隐私和认证 | 隐私影响分析、认证路径、风险分级 | 硬件形态、无线能力、数据流 | 合规清单、隐私策略草案、审批建议 | 读写合规文档 | 高风险场景不被遗漏 |
| Security Agent | 安全和权限 | 威胁建模、密钥管理、漏洞复盘 | 架构图、接口、日志 | 威胁模型、安全清单、修复建议 | 安全扫描和文档写入 | 每个外部接口有认证和审计 |
| Finance Agent | 预算和经营模型 | BOM 成本、现金流、定价、毛利测算 | BOM、报价、销售假设 | 财务模型、预算预警、单台经济性 | 更新财务表, 不付款 | 单台毛利和现金缺口可见 |
| Marketing Agent | 品牌和获客 | 定位、内容、落地页、发布节奏 | PRD、用户画像、竞品资料 | 品牌叙事、内容日历、发布素材 | 起草内容, 不自动公开发布 | 每条内容对应目标用户和转化目标 |
| Sales Agent | 销售和客户开发 | ICP、线索评分、邮件草稿、Demo 脚本 | 客户列表、访谈记录、产品资料 | 销售话术、跟进计划、CRM 更新 | 维护 CRM, 对外发送需审批 | 合格线索数和跟进率 |
| Customer Success Agent | 试点客户成功 | 入门流程、反馈归类、问题优先级 | 试点日志、客户反馈、工单 | 反馈摘要、功能建议、续约风险 | 更新反馈库和 issue | 关键反馈进入产品路线图 |
| Knowledge Ops Agent | 知识库和流程 | 文档去重、决策记录、上下文打包 | 所有文档、会议纪要、issue | 决策日志、周报、上下文索引 | 维护仓库文档 | 新任务能找到上下文 |

## 6. Agent 协作工作流

### 6.1 从想法到任务

1. 创始人通过硬件语音或控制台提出目标。
2. Orchestrator 把目标拆成战略、产品、技术、合规和商业问题。
3. CEO Strategy Agent 判断是否符合当前季度目标。
4. Product Manager Agent 产出需求和验收标准。
5. Hardware、Firmware、Backend、AI、UX Agents 分别产出方案。
6. Compliance、Security、Finance Agents 做风险和成本审查。
7. 创始人审批后, Knowledge Ops Agent 写入 GitHub 文档和 issue。

### 6.2 从任务到交付

```text
PRD -> architecture note -> implementation issue -> test evidence -> release note -> postmortem
```

每个任务必须具备:

- 明确的用户问题。
- 可运行或可检查的验收方式。
- 成本、隐私、安全和合规风险分级。
- 负责人 Agent 和最终人类审批人。
- 完成后的证据链接。

### 6.3 周期节奏

每日:

- Knowledge Ops Agent 汇总昨日变更和未决审批。
- QA Reliability Agent 汇总失败测试、缺陷和风险。
- CEO Strategy Agent 给出当天最高优先级。

每周:

- Product Manager Agent 复盘用户反馈。
- Finance Agent 更新现金流和单台成本。
- Supply Chain Agent 更新关键器件风险。
- Compliance 和 Security Agents 更新风险清单。

每月:

- 创始人审批路线图调整。
- Agents 输出经营复盘: 目标、结果、偏差、下月实验。

## 7. 数据和记忆架构

建议维护以下事实源:

| 数据域 | 推荐文件或系统 | 维护 Agent |
|---|---|---|
| 公司目标 | `docs/strategy/okr.md` | CEO Strategy Agent |
| 产品需求 | `docs/product/prd.md` | Product Manager Agent |
| 用户反馈 | `docs/research/customer-feedback.md` | Customer Success Agent |
| 决策记录 | `docs/decisions/` | Knowledge Ops Agent |
| 硬件方案 | `docs/hardware/` | Hardware Architect Agent |
| BOM 和供应商 | `docs/supply-chain/` | Supply Chain Agent |
| 测试证据 | `docs/quality/` | QA Reliability Agent |
| 合规和隐私 | `docs/compliance/` | Compliance Agent |
| 安全模型 | `docs/security/` | Security Agent |
| 财务模型 | `docs/finance/` | Finance Agent |
| 市场销售 | `docs/go-to-market/` | Marketing 和 Sales Agents |

记忆原则:

- 战略结论和技术决策必须写入仓库, 不能只留在聊天记录。
- 每条关键决策记录要包含背景、选项、取舍、结论、审批人和日期。
- Agent 可以引用历史结论, 但当前市场、法规、价格和供应商信息需要重新验证。

## 8. 技术架构建议

### 8.1 硬件 MVP

推荐模块:

- 主控: Linux SBC 或高性能 MCU 加协处理器。早期优先开发便利性, 不急于极限成本。
- 音频: 麦克风阵列、回声消除、物理静音键。
- 视觉: 低功耗摄像头或可选视觉模块, 默认保护隐私。
- 输出: 小屏幕、LED 状态灯或触控按键。
- 连接: Wi-Fi 和 BLE。蜂窝网络作为后续版本。
- 安全: 安全启动、设备身份、密钥存储、OTA 回滚。
- 结构: 可 3D 打印外壳或开发板外壳先验证使用场景。

### 8.2 软件 MVP

推荐模块:

- Device Agent: 采集音频、设备状态、传感器事件和用户确认。
- Local Runtime: 唤醒词、基础降噪、离线缓存、隐私状态控制。
- Cloud Orchestrator: Agent 路由、任务队列、审批门禁、审计日志。
- Agent Workspace: 每个角色 Agent 的指令、工具、记忆和指标。
- Founder Console: 任务、审批、路线图、客户反馈、财务和风险视图。
- Evaluation Harness: 模型输出评估、工具调用回放、失败案例库。

### 8.3 Agent 工具边界

允许自动执行:

- 检索仓库文档。
- 起草 PRD、方案、邮件、脚本和测试计划。
- 创建本地文件、运行测试、生成报告。
- 整理客户反馈和供应商信息。

必须人工审批:

- 付款、下单、合同、招聘、融资和法律文件。
- 对外发送邮件、发布营销内容、公开路线图。
- 收集或处理敏感个人数据。
- 更改安全策略、隐私策略和合规结论。
- 量产承诺和客户交付承诺。

## 9. 开发路线图

### Phase 0: OPC 基础设施, 第 1 到 2 周

目标:

- 建立 GitHub 仓库、文档结构、Agent 角色定义和决策记录机制。
- 完成 10 个目标用户访谈问题和 3 个候选产品场景。
- 明确 MVP 不做什么。

交付物:

- Agent 角色矩阵。
- 产品假设清单。
- 初版 PRD。
- 风险登记册。
- Codex `/goal` 任务书。

通过标准:

- 任意新任务都能被路由到明确 Agent。
- 创始人能在 30 分钟内判断下一步最高优先级。

### Phase 1: 概念验证 POC, 第 3 到 6 周

目标:

- 使用现成开发板和外设做可演示原型。
- 完成语音指令到 Agent 任务的最小闭环。
- 建立云端 Orchestrator 和创始人审批流。

交付物:

- 设备输入 Demo。
- Agent 任务队列 Demo。
- PRD v1。
- 系统架构图。
- 初版评估集。

通过标准:

- 创始人能通过硬件入口创建任务。
- 至少 3 个 Agent 能协作生成可审阅交付物。
- 审批和审计日志可追踪。

### Phase 2: EVT 工程验证, 第 7 到 14 周

目标:

- 从开发板原型过渡到工程样机。
- 明确核心器件、功耗、热、音频和连接稳定性。
- 完成第一轮真实用户试点。

交付物:

- EVT 样机 3 到 10 台。
- BOM v1 和替代料清单。
- 固件架构和 OTA 策略。
- 可靠性测试计划。
- 隐私和安全威胁模型。

通过标准:

- 样机可连续运行目标时长。
- 关键器件有替代路径。
- 用户试点反馈能回到 PRD 和路线图。

### Phase 3: DVT 设计验证, 第 15 到 26 周

目标:

- 稳定工业设计、结构、固件、云端服务和 App 控制台。
- 跑完合规准备清单和安全检查。
- 形成小批量试产计划。

交付物:

- DVT 样机。
- 测试矩阵和缺陷闭环。
- 隐私策略和用户协议草案。
- 供应商短名单。
- 单台经济性模型。

通过标准:

- 高优先级缺陷可控。
- 单台成本和毛利区间有证据。
- 合规路径没有阻塞项。

### Phase 4: PVT 试产验证, 第 27 到 38 周

目标:

- 完成小批量试产、包装、质检、售后流程。
- 验证供应链和生产测试工装。
- 准备上市或封闭预售。

交付物:

- PVT 批次。
- 生产测试流程。
- 售后问题分类和处理 SOP。
- 发布材料。
- 销售和客户成功流程。

通过标准:

- 生产良率达到内部阈值。
- 售后流程可由 Agent 辅助执行。
- 创始人能看到现金流、库存和客户风险。

### Phase 5: Launch 与 OPC 运营, 第 39 周以后

目标:

- 上线产品并维持 Agent 驱动的经营节奏。
- 建立客户反馈到产品改进的闭环。
- 优化成本、质量和获客。

交付物:

- 发布版本。
- 运营仪表盘。
- 月度经营复盘。
- 产品迭代计划。
- 安全和合规复审记录。

通过标准:

- 核心经营指标每周更新。
- 客户反馈能在 7 天内进入处理状态。
- 关键经营动作均有审批和证据。

## 10. 关键风险和控制

| 风险 | 表现 | 控制方式 |
|---|---|---|
| 产品定位过宽 | 什么都想做, MVP 无法落地 | 每阶段只服务 1 到 2 个核心场景 |
| Agent 角色泛化 | 每个 Agent 都像通用聊天助手 | 每个 Agent 必须有输入、输出、工具和指标 |
| 硬件成本失控 | 原型能跑, 但无法量产 | EVT 前维护 BOM 和替代料 |
| 隐私信任不足 | 用户担心麦克风和摄像头 | 物理静音、状态可见、默认最小采集 |
| 合规误判 | 上市前发现认证或隐私阻塞 | Compliance Agent 从 POC 阶段参与 |
| 一人公司过载 | 创始人审批和决策堆积 | 只把高风险动作交给创始人审批 |
| 模型成本失控 | 每个任务都走昂贵模型 | AI ML Agent 维护模型路由和成本预算 |
| 供应链单点 | 关键器件断供 | 关键料至少两个来源或替代方案 |

## 11. 90 天优先行动

第 1 到 14 天:

- 固化本仓库文档结构。
- 明确目标用户和 3 个使用场景。
- 写出 PRD v1 和 Agent 角色矩阵。
- 建立决策记录和风险登记册。

第 15 到 45 天:

- 做硬件 POC。
- 实现语音输入到 Agent 任务队列的闭环。
- 完成 5 到 10 次用户访谈。
- 建立基础财务模型和 BOM 初稿。

第 46 到 90 天:

- 迭代可演示样机。
- 完成云端 Orchestrator 和审批流。
- 跑第一轮试点。
- 决定是否进入 EVT。

## 12. 成功标准

第一阶段成功不是“有一个炫酷 Demo”, 而是满足以下条件:

- 产品只服务一个清晰人群和一个高频痛点。
- 硬件入口能稳定触发 Agent 工作流。
- 多角色 Agents 能产出可审阅、可追踪、可验证的工作成果。
- 创始人只处理判断、审批和关系型工作, 不被重复性文档和协调拖垮。
- 每个阶段的继续投入都有证据支持。
